# งาน 4: บอร์ดคำขอหาติวเตอร์ + offer

วันที่: 2026-11-09 · สถานะ: รออนุมัติ · ฐาน: `main` (`adda1cd`)

## เจตนา

ตอนนี้ Tewtopia มีทางเดียว: นักเรียนหาติวเตอร์ งานนี้เพิ่มทางกลับ — นักเรียนที่หาไม่เจอโพสต์สิ่งที่ต้องการ
ติวเตอร์เข้ามาเลือกโพสต์แล้วยื่นราคา นักเรียนเลือกรับ แล้วทั้งคู่ได้ช่องทางติดต่อกัน
ให้ติวเตอร์มีเหตุผลกลับมาที่เว็บ และนักเรียนไม่ต้องไล่ดูการ์ดทีละคน

## Flow (จากผู้ใช้)

1. **นักเรียนโพสต์คำขอ**: วิชา (checkbox), ระดับชั้น (checkbox), เนื้อหาคร่าวๆ, วัน/เวลาเรียน, รูปแบบการเรียน (online/onsite ฯลฯ)
   — ต้องมีช่องทางติดต่ออย่างน้อย 1 ช่อง (IG / Facebook / โทร / Line — แบบเดียวกับติวเตอร์) ก่อนโพสต์ได้
2. **ติวเตอร์คลิกโพสต์บนบอร์ด** → modal (แบบเดียวกับ modal ติวเตอร์) → ใส่ราคาต่อชั่วโมง → กดส่ง offer
3. **นักเรียนเห็น offer** → กด **Accept**
4. **ติวเตอร์ได้รับแจ้งเตือน**ว่า offer ถูก accept
5. **นักเรียน**: หน้า offer แสดงสถานะ Accepted → คลิกเปิด modal ติวเตอร์พร้อมช่องทางติดต่อ (flow เดียวกับ Find tutors)
6. **ติวเตอร์**: หน้า offer ของตัวเองแสดง Accepted → คลิกดูข้อมูลนักเรียน (รวมช่องทางติดต่อ)
7. **โพสต์ยังเปิดอยู่หลัง accept** — นักเรียน accept ได้หลาย offer — จนกว่า**นักเรียนหรือติวเตอร์**กดยืนยันว่า deal สำเร็จ

## เป้าหมาย

- นักเรียนโพสต์ / ยกเลิกโพสต์ / ดู offer / accept / ยืนยัน deal ได้
- ติวเตอร์ดูบอร์ด / ยื่น offer / แก้ราคา offer / ดู offer ของตัวเอง / ยืนยัน deal ได้
- ช่องทางติดต่อของทั้งสองฝ่ายเปิดเฉพาะคู่ที่ offer ถูก accept แล้ว
- แจ้งเตือนในเว็บ (ตัวเลขบน tab) ให้ทั้งสองฝ่ายรู้ว่ามีอะไรต้องดู

## ไม่อยู่ในงานนี้

- แจ้งเตือนทางอีเมล / push (ทำหลังต่อ SMTP)
- แชทในเว็บ, นัดเวลาเรียน (`sessions`), รีวิว, จ่ายเงิน
- ค้นหา/กรองบอร์ด, จับคู่อัตโนมัติ
- ใช้ตาราง `tutor_requests` / `matches` เดิม (โมเดลเดิมเป็น "ส่งถึงติวเตอร์คนเดียว" ไม่ตรงกับบอร์ด — ปล่อยไว้ไม่แตะ)

## สิ่งที่ห้ามเกิด

- ช่องทางติดต่อหรือชื่อของนักเรียนหลุดไปถึงใครก็ตามที่ไม่ใช่ติวเตอร์ที่ถูก accept (นักเรียนอาจเป็นเด็ก)
- ช่องทางติดต่อของติวเตอร์หลุดไปถึงนักเรียนผ่าน offer ก่อนที่ติวเตอร์จะอยู่ใน Find tutors (ใช้กฎเดิม: ติวเตอร์ที่ยื่น offer ได้ต้อง "listed")
- ผู้ใช้แก้สถานะ offer/โพสต์ของคนอื่น หรือข้ามขั้นสถานะ (เช่น ติวเตอร์ accept offer ตัวเอง)

## สิ่งที่ตัดสินใจแล้ว

### จากผู้ใช้
- ฟิลด์ของโพสต์ตาม flow ข้อ 1; ช่องทางติดต่อนักเรียน 4 ช่องแบบติวเตอร์ ต้องมีอย่างน้อย 1
- offer มีราคาต่อชั่วโมง; modal แบบเดียวกับ Find tutors
- accept หลาย offer ได้; โพสต์เปิดจนกว่าฝ่ายใดฝ่ายหนึ่งยืนยัน deal สำเร็จ
- หลัง accept ทั้งสองฝ่ายดูข้อมูลอีกฝ่ายได้จากหน้า offer
- **ไม่มีช่องงบประมาณในโพสต์** — ไม่อยากให้บอร์ดกลายเป็นที่ตั้งมาตรฐานราคา; ราคามาจาก offer ของติวเตอร์เท่านั้น
  และราคาใน offer เห็นเฉพาะนักเรียนเจ้าของโพสต์ (ไม่แสดงบนบอร์ดสาธารณะหรือให้ติวเตอร์คนอื่นเห็น)
- **ราคาใน offer เป็นตัวเลขเดียว** บังคับทุกครั้งที่ส่ง — นักเรียนเห็นในการ์ด offer
- **ราคาในโปรไฟล์ติวเตอร์เปลี่ยนเป็นช่วง** ต่ำสุด–สูงสุดต่อชั่วโมง (เช่น 300–500 THB/hr) แสดงบนการ์ด Find tutors
- **ราคาขั้นต่ำ 250 THB/hr** กันตัดราคากันเกินไป

### ผลต่องานที่ทำไปแล้ว + รายละเอียดราคา (จากผม — ผู้ใช้ตรวจได้)
- ขั้นต่ำ 250 ใช้กับ **ทั้งช่วงราคาในโปรไฟล์และราคาใน offer** (ไม่อย่างนั้นติวเตอร์ตั้งโปรไฟล์ 250 แล้วเสนอ 100 ได้) — บังคับทั้งที่ฟอร์มและใน DB (check constraint)
- โปรไฟล์: `hourly_rate_min` ≥ 250 และ `hourly_rate_max` ≥ `hourly_rate_min`; ใส่ค่าเดียวก็ได้ (min = max → แสดง "500 THB/hr")
- offer ไม่ต้องอยู่ในช่วงของโปรไฟล์ — ขอแค่ ≥ 250
- **ย้ายข้อมูลเดิม**: คอลัมน์ `hourly_rate` เดิม → `hourly_rate_min` = `hourly_rate_max` = ค่าเดิม; ติวเตอร์ที่ค่าเดิมต่ำกว่า 250 จะ**หายจาก Find tutors** จนกว่าจะแก้ราคา
  (กฎ listing เปลี่ยนจาก "ราคา > 0" เป็น "ช่วงราคาถูกต้องและ ≥ 250"; checklist ใน Dashboard/Profile ใช้กฎเดียวกัน)
- `public_tutor_cards` เปลี่ยนคอลัมน์ราคาเป็น `hourly_rate_min` / `hourly_rate_max` (ต้อง drop แล้วสร้าง view ใหม่ เพราะเปลี่ยนชื่อคอลัมน์)
- การ์ด offer ไม่ต้องแสดงราคาโปรไฟล์คู่กัน — นักเรียนกดดูการ์ดติวเตอร์เพื่อเห็นช่วงราคาได้
- ทบทวนเรื่องงบประมาณนักเรียนอีกครั้งเมื่อมีผู้ใช้จริง — ตัวเลือกที่เก็บไว้: งบส่วนตัวที่ติวเตอร์มองไม่เห็น ใช้ติดป้าย "เกินงบ" ให้นักเรียน

### จากผม (ผู้ใช้ตรวจได้)

**ข้อมูล**
- ตาราง `student_requests`: `id`, `student_user_id` → profiles, `subjects text[]` (ค่าจากตาราง `subjects` ที่มีอยู่, ≥1),
  `teaching_levels text[]` (5 ค่าเดิม, ≥1), `details text` (≤1000 ตัวอักษร, ไม่บังคับ), `schedule text` (≤200, บังคับ — ข้อความอิสระเช่น "เสาร์-อาทิตย์ บ่าย"),
  `teaching_modes text[]` (online / in_person / group / hybrid, ≥1), `status` (`open` | `closed` | `cancelled`), `created_at`, `updated_at`
- ตาราง `request_offers`: `id`, `request_id`, `tutor_user_id`, `hourly_rate integer >= 250`, `status`
  (`pending` | `accepted` | `declined` | `deal_done` | `closed` | `withdrawn`), timestamps; unique (`request_id`, `tutor_user_id`) — ติวเตอร์ยื่นได้ 1 offer ต่อโพสต์
- ช่องทางติดต่อนักเรียน: คอลัมน์ `contact_*` 4 ช่องบน `student_profiles` (ตารางมีอยู่แล้ว) — กรอกครั้งเดียว ใช้ทุกโพสต์;
  ถ้ายังไม่มี ฟอร์มโพสต์แสดงช่องให้กรอกในหน้าเดียวกัน; แก้ได้ในหน้า Profile ของนักเรียน

**สถานะ**
- offer: `pending` → (นักเรียน accept) `accepted` → (ฝ่ายใดยืนยัน) `deal_done`
- ติวเตอร์แก้ราคาได้ขณะ `pending`; ถอนได้ขณะ `pending` → `withdrawn`
- เมื่อ offer ใดเป็น `deal_done`: โพสต์ → `closed`; offer อื่นในโพสต์ที่ `pending`/`accepted` → `closed`
- นักเรียนยกเลิกโพสต์ที่ `open` ได้ → `cancelled`; offer `pending`/`accepted` ทั้งหมด → `closed`
- **ทุกการเปลี่ยนสถานะทำผ่านฟังก์ชัน DB (security definer) ที่ตรวจว่าใครทำอะไรได้** — ไม่เปิด policy update ตรงๆ บนสองตารางนี้
  (`create_request`, `cancel_request`, `submit_offer` (สร้าง, แก้ราคา, หรือยื่นใหม่หลังถอน), `withdraw_offer`, `accept_offer`, `decline_offer`, `confirm_deal`)

**ใครเห็นอะไร**
- **บอร์ด (`/requests`) เปิดให้ทุกคนดู ไม่ต้องล็อกอิน** (ตรงกับงาน 2: "ฝั่งติวเตอร์เห็น list request")
  แสดงเฉพาะโพสต์ `open`: วิชา, ระดับ, เนื้อหา, วันเวลา, รูปแบบ, วันที่โพสต์, จำนวน offer — **ไม่แสดงชื่อหรือข้อมูลใดของนักเรียน**
  ผ่าน view `public_request_cards` แบบเดียวกับ `public_tutor_cards`
- ยื่น offer ได้เฉพาะติวเตอร์ที่ล็อกอินและ listed (ผ่าน `public_tutor_cards`); guest/นักเรียน กดแล้วเห็นข้อความ + ลิงก์ล็อกอิน (`next` กลับ modal เดิม: `/requests?request=<id>`)
- นักเรียนเห็น offer ในโพสต์ของตัวเอง: ชื่อติวเตอร์, ราคาที่เสนอ, สถานะ + เปิดการ์ดติวเตอร์ได้ (ข้อมูลจาก `public_tutor_cards`)
  — ช่องทางติดต่อติวเตอร์ขึ้นเมื่อ offer เป็น `accepted`/`deal_done`
- ติวเตอร์เห็นนักเรียน (ชื่อที่แสดง + ช่องทางติดต่อ) เฉพาะเมื่อ offer ของตัวเองเป็น `accepted`/`deal_done`
  ผ่านฟังก์ชัน `get_offer_counterpart(offer_id)`

**หน้าและเมนู**
- `/requests` — บอร์ด (สาธารณะ) + modal ต่อโพสต์ (URL `?request=<id>`)
- `/main/requests` — นักเรียน: ปุ่ม "Post a request", รายการโพสต์ของฉัน, offer ในแต่ละโพสต์ (Accept / Confirm deal / ดูติวเตอร์), ยกเลิกโพสต์
- `/main/requests/new` — ฟอร์มโพสต์
- `/main/offers` — ติวเตอร์: offer ทั้งหมดของฉันพร้อมสถานะ (แก้ราคา / ถอน / Confirm deal / ดูนักเรียน)
- tab นักเรียน: Dashboard · Find tutors · **My requests** · Profile · Settings
- tab ติวเตอร์: Dashboard · **Request board** · **My offers** · Tutor profile · Settings
  (Profile ของติวเตอร์ย้ายไปเป็นลิงก์ในหน้า Tutor profile เพื่อไม่ให้ tab ยาวเกิน)
- guest: Find tutors · **Request board**

**แจ้งเตือนในเว็บ (ตัวเลขบน tab)**
- นักเรียน — "My requests": จำนวน offer `pending` ในโพสต์ `open`
- ติวเตอร์ — "My offers": จำนวน offer `accepted` (ยังไม่ `deal_done`)
- ไม่เก็บสถานะ "อ่านแล้ว" — ตัวเลขหายเมื่อจัดการเสร็จ (accept / confirm deal)

**รายละเอียดที่ผมตัดสินใจหลัง reviewer อ่าน (ผู้ใช้ตรวจได้)**
- **ช่องทางติดต่อติวเตอร์**: ไม่ได้ซ่อนเพิ่ม — นักเรียนที่ล็อกอินเห็นได้อยู่แล้วจาก Find tutors (งาน 3) การ "เปิดเมื่อ accepted" ใช้กับ**ช่องทางติดต่อนักเรียน**เท่านั้น
  ในหน้า offer ของนักเรียน ปุ่มดูช่องทางติดต่อติวเตอร์จะแสดงเมื่อ offer เป็น accepted/deal_done (เป็นเรื่อง UI ไม่ใช่สิทธิ์ใหม่)
- **นักเรียนปฏิเสธ offer ได้** ทั้งขณะ `pending` และหลัง `accepted` → สถานะใหม่ `declined` — กด accept ผิดก็ถอนได้
  และติวเตอร์จะเห็นช่องทางติดต่อนักเรียนไม่ได้อีก (`get_offer_counterpart` ให้ข้อมูลเฉพาะ `accepted` / `deal_done`)
- **ติวเตอร์ถอนแล้วยื่นใหม่ได้**: `submit_offer` บนแถวที่ `withdrawn` จะเปลี่ยนกลับเป็น `pending` พร้อมราคาใหม่ (แถว `declined` / `closed` ยื่นใหม่ไม่ได้)
- **เช็กสิทธิ์ตามสถานะปัจจุบัน ณ ตอนทำ**: `create_request` ต้องเป็น role student; `submit_offer` ต้องเป็นติวเตอร์ที่ listed ณ ตอนนั้น;
  `accept_offer` ต้องให้ติวเตอร์ยัง listed อยู่ (ไม่ listed → ปฏิเสธพร้อมข้อความ)
  — offer ที่ accepted ไปแล้วไม่ถูกยกเลิกเมื่อติวเตอร์เลิก listed หรือเปลี่ยน role; สองฝ่ายยังเห็นกันได้จนกว่าจะ decline / deal / ยกเลิกโพสต์
- **test DB**: เพิ่ม `@electric-sql/pglite` เป็น **devDependency** (ไม่ใช่ runtime) และย้าย harness ที่ใช้ทดสอบงาน 2–3 เข้ามาใน repo
  (`supabase/tests/`) พร้อม stub `auth.users` / `auth.uid()` / `auth.role()` — รันด้วย `npm run test:db`

## ข้อจำกัด

- Next.js 15, Supabase, Tailwind v4 — ไม่เพิ่ม runtime dependency (devDependency สำหรับ test DB ได้)
- `schema.sql` ยังต้องรันซ้ำได้; ใช้รูปแบบเดียวกับงาน 2–3 (view สาธารณะ + ฟังก์ชัน security definer + test ใน PGlite)
- ใช้ `ui` tokens, `TopNav`, รูปแบบ modal `<dialog>` จาก `tutor-browser.tsx`, helper ช่องทางติดต่อ `tutor-contact.ts` (แยกชื่อให้ใช้ได้ทั้งสองฝ่าย)

## ปล่อยให้ผู้สร้างตัดสินใจ

- ชื่อไฟล์/component, การแชร์ modal ระหว่าง `/tutors` กับ `/requests`
- ข้อความ UI ที่ไม่ได้ระบุ, ลำดับการเรียงรายการ (ค่าเริ่มต้น: ใหม่สุดก่อน)
- ตำแหน่งปุ่ม Accept / Confirm deal ในหน้ารายการ

## การตรวจรับ

1. guest เปิด `/requests` เห็นโพสต์ `open` โดยไม่มีชื่อ/ช่องทางติดต่อนักเรียนใน HTML หรือ response
2. นักเรียนที่ยังไม่มีช่องทางติดต่อ โพสต์ไม่ได้จนกรอกอย่างน้อย 1 ช่อง
3. ติวเตอร์ที่ listed ยื่น offer ได้, แก้ราคาได้ขณะ pending, ยื่นซ้ำโพสต์เดิมไม่ได้; ติวเตอร์ที่ไม่ listed และนักเรียนยื่นไม่ได้
4. นักเรียน accept → ติวเตอร์เห็นตัวเลขบน "My offers" และเห็นช่องทางติดต่อนักเรียน; นักเรียนเห็นช่องทางติดต่อติวเตอร์
5. ติวเตอร์ที่ offer ยัง pending หรือถูกปิด ดูช่องทางติดต่อนักเรียนไม่ได้ (ทดสอบผ่านฟังก์ชันโดยตรง)
6. confirm deal (จากฝ่ายใดก็ได้) → โพสต์หายจากบอร์ด, offer อื่นเป็น closed
7. ยกเลิกโพสต์ → หายจากบอร์ด, offer ทั้งหมด closed
8. ผู้ใช้เรียกฟังก์ชันเปลี่ยนสถานะของโพสต์/offer ที่ไม่ใช่ของตัวเองแล้วถูกปฏิเสธ
9. test, build, lint, typecheck ผ่าน; test DB ใน PGlite ครอบคลุมข้อ 3–8

## เปลี่ยนหลังอนุมัติ (2026-11-09, ตามที่ผู้ใช้ขอ)

- **การ์ดบนบอร์ดแสดงชื่อที่แสดง (display name) ของนักเรียน** — แทนที่ข้อ "ไม่แสดงชื่อนักเรียนบนบอร์ด"
